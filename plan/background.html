论文线方案（papers 仓） · 日志线方案 · 重建背景

块笔记废弃 · 论文库与日志重建背景

2026-10-12 · gwb-apps 单元 · 状态：待两个决策点拍板（见文末）· 这份背景在 gwb-papers 与 gwb-journal 两仓的 plan/ 下各存一份相同内容，各自的方案页在旁边；不建文档站（文档站自身在重写）

整套块笔记（gwb-block-note 的核心与全部 bn-* 插件，以及 gwb-paper-fetch 里的论文库插件）标记废弃。论文库与日志各起一个全新插件、起全新名字、完全重写，不在旧代码上改。两条线并行推进，互不依赖。

一、为什么废弃

  • 平台里又造了一个平台。块笔记核心 gwb-bn-core 约 3.9 万行（316 个文件），自带存储、字段声明、提交与冲突、历史撤销、JS 查询引擎、正文渲染；而它服务的所有领域插件加起来（日志 4.4k + 标签 2.6k + 评论 1.2k + 论文库 14k 行）还不如核心大。地基比楼大。
  • 模型错配，而且代价是持续付的。日志本质是时间序列，论文本质是关系数据（作者—机构多对多、参考文献与被引是图上的边），都不长在「五字段块树」上。为了塞进树，日志的一天要用特殊顶级块 + 唯一日期字段 + ifAbsent 创建语义；论文的作者机构要做成独立块文件。说明书里大量篇幅是在教 agent 跟块模型周旋，而不是领域本身的事。
  • 通用性没有兑现。跨域引用、统一查询这些通用模型的卖点，实际工作流里几乎没用到；用到的引用都在论文域内部。
  • 抽象没消掉复杂度，只是把它搬进了规约。领域复杂度变成了每份说明书里的规程，靠 agent 读文档来执行，负担是复利式的。

二、重写的总则（两条线共同遵守）

★ 要点：UI 设计照搬——废弃的是模型，不是界面

日志与论文两个插件现有的界面设计是好的，直接搬到新插件：日志的月历窗格、正文窗格、全库待办、状态栏快速记录；论文的列表筛选排序、题录卡、引用页与下一批推荐。交互与布局不重新设计，只把底下的数据源从块库换成新模型。（论文的阅读界面与评论仍整体推迟，不在照搬范围。）

  1. 完全重写实现，但继承行为规格。论文收集管线里真正贵的是摸索出来的规则（各家接口怎么解析、IEEE 与知网怎么下、翻译逐行怎么对位），它们活在旧仓的附件说明书与测试里，重写时当规格输入照搬，不凭印象重推。
  2. 起全新名字。新插件名不带 bn- 前缀、与旧名不撞。agent 是靠 skill 名与命令前缀找说明书的，旧名字活着就会有会话按旧说明书往旧库写。新名字即新契约。
  3. 新插件落在 evew5-gwbapps 单元新建插件仓，不开新单元。名字已定：论文线 papers（仓 gwb-papers、包 @godcreator/gwb-papers、命令前缀 papers.）、日志线 journal（仓 gwb-journal、包 @godcreator/gwb-journal、命令前缀 journal.）。两个仓已建好，构建与检查全绿；不建文档站（文档站在重写）。
  4. 旧插件打废弃标记但不马上卸载。六个 bn-* 插件与旧论文库插件：README 与 SKILL 开头加「已废弃、继任者是谁、数据在哪」，发一版只升 y 的更新。default home 在迁移期内保留旧件——数据还在旧块库里，卸了就读不出来。
  5. 论文材料布局原样沿用。y4hhy-paper-library 的 papers/<文件夹>/（responses、pdf、raw、md、translate、assets）与块无关且已稳定，不搬不重构。
  6. 阅读与评论整体推迟。论文这一阶段不设计在哪读、怎么读、怎么评论；日志的界面归属单独处理（见日志线）。
  7. 每条线各自迁移对账，全绿后才退役旧件（default home 卸载，旧仓转归档状态）。

三、两条并行线

线这一阶段做什么明确不做方案
论文库 papers 自己的论文数据库（新索引）＋ 入库完整功能：查询、题录导入、下载、转换、翻译、材料核对、读与列的命令 阅读界面、评论、正文拆段导入（body.import 整个消失）、作者机构实体化 gwb-papers 仓 plan/papers.html
日志 journal 一天一个 mdx 文件的新插件：格式定义、月历与统计、记一笔排待办勾待办、快速记录、旧数据迁移 撤销历史（建议接受没有）、通用标签与评论、任何查询引擎 本仓 plan/journal.html

两条线共享的只有两件事：命名与废弃标记（已做掉），以及最后退役旧件。除此之外互相不等待、不阻塞。

五、已拍板的决策点（2026-10-12）

决策一：普通笔记不迁移，留在旧块库里封存

notes 库整个不动，随块笔记一起退役封存。bn-tags、bn-comment 没有残存用户，journal 与 papers 各自迁移对账后即可把 bn-* 全部卸载。J4 只迁日志数据，P3 只迁论文题录、标签与评论里的失败原因。

决策二：不需要撤销历史

文件与索引就是真相，写错了改回来；不引入 git、提交历史或任何撤销机制。
